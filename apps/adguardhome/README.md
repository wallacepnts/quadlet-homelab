# AdGuard Home — Podman Quadlet (rootless)

**[🇧🇷 Leia em português](./README.pt-BR.md)**

An [AdGuard Home](https://github.com/AdguardTeam/AdGuardHome) (a recursive
DNS server that blocks ads and trackers for the whole network) deploy via
Podman Quadlet, following the
[official Docker guide](https://github.com/AdguardTeam/AdGuardHome/wiki/Docker).

## Architecture

A single container, running as root internally (the image's own default — it
needs that to open port 53 inside its own network namespace; it is not the
host's real root, see the privileged-port section). A **bridge** network, not
`host` (the official wiki only recommends `host` for DHCP or for seeing each
client's real IP in the statistics — the same deliberate trade-off already
made for [Syncthing](../syncthing/)/Jellyfin: no built-in DHCP, and the
per-client statistics show the IP of Podman's bridge network gateway rather
than each LAN device's IP; ad blocking for the whole network works normally,
which is this deploy's main use).

Two volumes: `conf` (the config generated by the installation wizard,
`AdGuardHome.yaml`) and `work` (runtime data — downloaded filters, statistics,
query logs).

**DNS on port `5335`, not the standard `53`** — a deliberate decision for this
deploy: rootless Podman does not publish privileged ports (<1024) without
touching a host sysctl (see the dedicated section further down), and that
change was deliberately left out of the default so as not to alter the host's
behaviour just for this service. The practical effect: **this deploy, as it
stands, does not work as the network's DNS resolver** — routers and most
operating systems only speak DNS on port 53, with no custom-port option. It
works for testing and manual use (`dig @<host-ip> -p 5335 example.com`, or
apps that accept a custom port). Anyone wanting the full use (DNS for the
whole network, with the router pointed here) makes the optional change
described in "Using the standard DNS port 53" below.

## Files

```
adguardhome.container     # main unit
```

No `.env.example` — the image does not use environment variables for
configuration (everything is done through the web wizard on the first run, see
below).

## Prerequisites

- Rootless Podman with systemd `--user` working

## Installation

```bash
python3 install.py adguardhome            # dry-run: shows what it will do
python3 install.py adguardhome --apply
```

For the local network only, `--access local`; on the tailnet and the LAN,
`--access both`. Adding `--href-local` points the dashboard link at the LAN.
The script creates the directories, writes the `.env`, generates the secrets,
fixes the volumes' ownership, starts the service and prints the address at the
end — see [Installing and operating](../../docs/installing.md).

Open the installation wizard at `http://<host-ip>:3006` (or through
[tsdproxy](../tsdproxy/) at `https://adguardhome.<your-tailnet>.ts.net`, for
administration only). In the wizard, **keep the admin interface's port at
`3000`** (the suggested default) — this `.container`'s `HealthCmd` tests
exactly that port from inside the container; changing it there breaks the
healthcheck. The internal DNS port can stay at `53` as usual (the suggested
default) — what changes is only the external mapping, so the host exposes it
on `5335` instead of `53` (see "Architecture" above).

## Testing and using it by hand (port 5335)

```bash
dig @<host-ip> -p 5335 example.com
```

To genuinely use it as a specific device's DNS, configure a resolver with a
custom port on it by hand (most operating systems and routers do not let you
choose a port in the standard DNS field — it works in apps and tools that
accept an explicit `host:port`).

## Using the standard DNS port 53 (optional, it changes the host's scope)

To use it as the real resolver for the whole network/LAN (pointing the router
or the devices straight at it, with no custom port), two optional changes:

**1. Allow rootless Podman to bind a privileged port** — the process that
binds port 53 on the host is one of your own user's (`rootlessport`), with no
`CAP_NET_BIND_SERVICE` by default:

```bash
echo "net.ipv4.ip_unprivileged_port_start=53" | sudo tee /etc/sysctl.d/99-adguardhome-port53.conf
sudo sysctl --system
```

A host-level change (it allows unprivileged binds on ports 53-1023 for
**any** of your user's processes, not just this container) — reversible by
deleting the file and running `sudo sysctl --system` again.

**2. Change the port mapping** in `adguardhome.container` — in the two
`PublishPort=5335:53/...` lines, replace `5335` with `53`:

```ini
PublishPort=53:53/tcp
PublishPort=53:53/udp
```

```bash
systemctl --user daemon-reload
systemctl --user restart adguardhome
```

Then point the devices' DNS (individually or, better, in the router's DHCP
settings so it applies to the whole network) at the **host's IP** (not the
container's) on port 53 — `192.168.1.X`, say. Because the network is a bridge
(not `host`), AdGuard only sees the Podman network gateway's IP as each
query's "client", not each device's real IP — global filters work normally,
only the per-client statistics and per-device rules have no practical effect
in this mode.

## Auto-update

No `AutoUpdate=` — an explicit tag (`v0.107.78`), bumped by hand
(rule 9 of the [conventions](../../docs/conventions.md)). DNS is critical infrastructure for the whole network (if it goes down,
nobody resolves any name — the same reasoning as
[ownCloud](../owncloud/)/[Radicale](../radicale/) for user data) — review by
hand before updating, even though the image has `wget` available for a real
`HealthCmd` (automatic rollback could be enabled if you want to take that
risk).

## Backup & recovery

```bash
systemctl --user stop adguardhome
tar -czf adguardhome-backup-$(date +%Y%m%d-%H%M%S).tar.gz \
  -C ~/.config/containers/volumes adguardhome
systemctl --user start adguardhome
```
